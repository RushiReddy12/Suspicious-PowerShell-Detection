# Analyst Investigation Runbook — Suspicious PowerShell Execution

## 1. Purpose

This runbook provides a structured investigation workflow for alerts generated by the Suspicious PowerShell Detection.

The objective is to determine whether the observed PowerShell activity is legitimate, suspicious, or potentially malicious.

A detection alert is an investigation starting point, not proof of compromise.

## 2. Alert Overview

**Alert name:** Suspicious PowerShell Execution Detected

**Data source:** DeviceProcessEvents

**Primary MITRE ATT&CK technique:** T1059.001 — PowerShell

**Detection indicators:**

- Encoded PowerShell command
- Execution policy bypass
- Hidden PowerShell window
- Multiple suspicious indicators in one process event

## 3. Initial Alert Review

When an alert is generated, collect the following information:

| Field | Investigation purpose |
|---|---|
| Timestamp | Establish when execution occurred |
| DeviceName | Identify the affected endpoint |
| AccountName | Identify the associated account |
| FileName | Confirm the PowerShell executable |
| ProcessCommandLine | Understand the executed command |
| InitiatingProcessFileName | Identify the parent process |
| InitiatingProcessCommandLine | Understand how PowerShell was launched |
| ProcessId | Correlate process activity |
| SuspiciousIndicatorCount | Understand the number of matching indicators |

## 4. Investigation Workflow

### Step 1 — Identify the affected device

- Confirm the device name.
- Check whether the device is a workstation or server.
- Identify its business function.
- Determine whether it is expected to run PowerShell automation.

### Step 2 — Investigate the account

- Identify the account associated with execution.
- Determine whether it is a standard user, administrator, or service account.
- Check whether the account normally performs administrative activities.
- Review related authentication activity if available.

### Step 3 — Analyze the PowerShell command line

Look for:

- Encoded command parameters.
- Execution policy bypass parameters.
- Hidden window parameters.
- Suspicious download or execution commands.
- Obfuscated command patterns.
- Unusual script paths or arguments.

Do not treat any individual parameter as proof of malicious activity.

### Step 4 — Investigate the parent process

Review the initiating process.

Examples:

| Parent process | Investigation consideration |
|---|---|
| explorer.exe | Check whether the user intentionally launched a script |
| winword.exe | Investigate possible Office-to-PowerShell execution |
| wscript.exe | Review script-based execution |
| cmd.exe | Examine the parent command and execution chain |
| SCCM-related process | Verify whether the activity belongs to an approved deployment |

A legitimate parent process does not automatically make its child process safe.

### Step 5 — Review surrounding activity

Where telemetry is available, investigate:

- Related process executions.
- Network connections.
- File creation and modification.
- Authentication events.
- Other alerts from the same device or account.
- Script files and their contents.

Build a timeline around the suspicious execution.

### Step 6 — Determine investigation outcome

Classify the activity based on collected evidence.

| Classification | Meaning |
|---|---|
| Benign | Activity is supported by legitimate operational evidence |
| Suspicious | Activity requires additional investigation |
| Malicious | Evidence supports malicious execution |
| Inconclusive | Available evidence is insufficient to determine intent |

## 5. Recommended Investigation Actions

### If activity is benign

- Record the business justification.
- Document the script and execution context.
- Identify whether a narrowly scoped tuning change is justified.
- Preserve the evidence supporting the decision.

### If activity is suspicious

- Investigate related processes and network activity.
- Check for other affected devices or accounts.
- Escalate according to the organization's incident response process.
- Preserve relevant telemetry.

### If activity is confirmed malicious

- Follow the organization's incident response procedures.
- Escalate to the incident response team.
- Consider containment actions according to organizational policy.
- Investigate potential lateral movement and additional execution.
- Document evidence and response actions.

Do not isolate devices or disable accounts solely because this detection generated an alert. Follow approved incident response procedures and authorization requirements.

### If activity is inconclusive

- Record the missing evidence.
- Continue investigation using available telemetry.
- Escalate if necessary.
- Avoid closing the alert as benign without supporting evidence.

## 6. Investigation Decision Flow

1. Alert generated.
2. Identify device and account.
3. Review PowerShell command line.
4. Investigate parent process.
5. Correlate surrounding activity.
6. Determine whether evidence supports benign, suspicious, malicious, or inconclusive classification.
7. Document findings and take appropriate action.

## 8. Important Considerations

- Encoded commands are not automatically malicious.
- Execution policy bypass is not proof of compromise.
- Hidden PowerShell execution can be legitimate automation.
- Multiple indicators increase investigative interest but do not establish malicious intent.
- Parent-process context is important but should not be used as the sole basis for closing an alert.
- All conclusions should be supported by evidence.
